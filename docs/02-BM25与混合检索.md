# BM25 与混合检索

## BM25 的打分方式

BM25 是在 TF-IDF 基础上改良的排序函数，对每个查询词计算三部分：

词频（TF）：词在文档里出现越多越相关，但增长是饱和的——出现 10 次不意味着
比出现 5 次相关一倍。饱和由参数 `k1` 控制，默认 1.5，k1 越小饱和越快。

逆文档频率（IDF）：词在越少的文档里出现，区分度越高。「的」出现在所有文档里，
几乎没有信息量；「efConstruction」只出现在一篇文档里，命中它就是强信号。

文档长度归一化：长文档天然更容易包含查询词，需要惩罚。参数 `b` 控制归一化
强度，默认 0.75，b=1 表示完全归一化，b=0 表示不归一化。

BM25 的分数没有固定范围，会随语料规模、文档长度分布漂移。同一个查询在
100 篇和 10000 篇文档上得到的分数不在一个量级，这一点在融合时非常关键。

一个常见陷阱：BM25 可能给出负分。当某个词在超过一半的文档里出现时，
IDF 计算会得到负值。负分结果没有排序意义，必须过滤掉，否则融合时会把
它们当成有效候选。

## 为什么必须混合检索

两路检索的失效模式是互补的：

向量检索擅长语义泛化。用户问「电脑开不了机」，能找到标题为「主机无法启动」
的文档。但它对专有名词、错误码、函数名、版本号这类字面量不敏感——这些词
在预训练语料里出现得少，embedding 对它们的表示很弱。

BM25 擅长精确命中。`ERR_CONN_REFUSED`、`efConstruction`、`bge-reranker-v2-m3`
这类词只要出现就能被精确匹配。但它完全不理解同义词，「内存泄漏」和
「内存溢出」在它眼里是两个毫不相干的词。

生产环境的查询往往同时包含两类成分：既有口语化的意图描述，又有关键的词法线索。
只保留一路，必然在其中一类查询上系统性失分。

## 中文分词

BM25 以词为索引单位，中文需要先分词。jieba 是常用选择，但它需要加载约 40MB
词典，冷启动有开销，且对技术新词切分不准——「RAGFlow」会被切成「RAG」「Flow」，
「efConstruction」会被切碎。

替代方案是字符二元组（bigram）：把「向量数据库」切成「向量 / 量数 / 数据 / 据库」。
这是 Lucene 的 CJKAnalyzer 处理中文的默认做法。它不依赖词典，对未登录词天然友好，
代价是索引体积大约膨胀 1.5 倍。在技术文档场景下，bigram 的召回表现通常和
jieba 相当甚至更好，因为技术术语的构词往往不符合自然语言习惯。

工程上更稳的做法是两者都支持：装了 jieba 就用，没装就降级到 bigram，
不让词典成为部署的硬依赖。

## 融合策略

两路召回之后要合并成一个排序，有三种常见做法。

**截断拼接**：向量取 top_k，BM25 取 top_k，去重后直接拼接。
问题在于拼接后的相对顺序由遍历顺序决定，没有任何意义，重排序模型看到的
是一个近乎随机的列表。

**分数归一化加权**：各自 min-max 归一化到 0 到 1，再加权求和。
问题是 min-max 依赖当前批次的最大最小值——如果一批结果里有一条特别高分，
其余全被压到接近 0，反而破坏了两路各自的相对关系。而且权重需要按数据分布
调整，换语料就得重调。

**RRF（倒数排名融合）**：只用排名，不用分数，公式为

    score(d) = Σ  weight_i / (k + rank_i(d))

其中 rank 从 1 开始，k 通常取 60。k 的作用是压低头部差异：k 越小，排第一的
结果优势越明显；k 越大，各路贡献越平均。

RRF 的根本优势是对量纲免疫。BM25 的分数是 8.7 还是 870，向量相似度是 0.82
还是 0.31，都不影响结果，只影响名次。这正好绕开了前面说的量纲不可比问题。

RRF 的代价是丢弃了分数里的置信度信息。两条分数 0.9 和 0.85 的候选，
在 RRF 眼里只有名次差别。当同一路内的分数区分度很重要时，这是损失。
实践中这个损失通常可以接受，因为跨路融合本来就不该比较绝对值。

## 双路命中的意义

RRF 里一个隐含的性质：如果一个文档同时被两路召回，它的分数是两路贡献之和，
自然排在只被一路召回的文档前面。这是符合直觉的——两个独立的判断标准都认为
它相关，置信度应该更高。这也是混合检索常能提升 MRR 的原因。
