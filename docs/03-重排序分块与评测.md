# 重排序、分块与评测

## Bi-Encoder 与 Cross-Encoder

向量检索用的是 Bi-Encoder：查询和文档分别编码成向量，然后算相似度。
文档向量可以离线算好存起来，查询时只算一次，所以能支撑百万级库。
代价是查询和文档之间没有任何交互——模型在看到查询之前就已经把文档的意思
压缩成一个向量了，细粒度的匹配信息丢失。

Cross-Encoder 把查询和文档拼成一条输入 `[CLS] query [SEP] doc [SEP]`
一起过模型，注意力机制能在 token 级别充分交互，精度明显更高。
代价是每条候选都要单独跑一次前向，成本随候选数线性增长，不可能用来做全库检索。

所以标准做法是两段式：Bi-Encoder 粗召回二十条，Cross-Encoder 精排取三条。
这就是「重排序」这一层存在的全部理由。

成本量级参考（十万 chunk 的库）：粗召回二十条约 5 毫秒；精排二十条在 CPU 上
约 600 毫秒，走 API 约 80 毫秒；如果试图对全库做精排，计算量是两万倍。

## 相关性阈值

精排之后有一个容易被忽略的问题：检索不到相关内容时怎么办。

如果无条件取 top 3，那么用户问一个知识库里根本没有的问题时，系统会硬塞三条
不相关的片段，模型基于这些片段一本正经地编出答案。这是 RAG 幻觉最主要的来源，
在 Prompt 里写「不要编造」基本没用。

正确做法是给重排序分数设一个阈值，低于阈值的片段直接丢弃；如果一条都不剩，
就直接返回「知识库中没有相关内容」，而不是交给模型。

这个改动的效果通常比调 Prompt 显著得多，因为它从源头切断了噪声上下文。

## 分块策略

chunk_size 太小，单块语义不完整，检索到也没法回答；太大，单块混入多个主题，
向量被平均掉，反而谁也匹配不准，还会占满上下文窗口。

中文技术文档的经验值在 400 到 800 字之间，具体要看文档结构。markdown 文档
优先按标题层级切，能保证每块主题单一；纯文本按段落切，段落过长再按句子切。

overlap 的作用是防止关键信息正好被切在边界上。比如「Python 的内存管理采用
引用计数」这句话如果被切开，前半句在前一块，后半句细节在后一块，两块的语义
都不完整。overlap 让相邻块有一段重叠，通常取 chunk_size 的 10%，即 50 字左右。

overlap 不是越大越好：它会让同一段内容在多个块里重复出现，检索时可能召回
三条内容几乎一样的片段，浪费上下文窗口，也干扰重排序。

## 评测指标

离线评测是整个 RAG 系统里最容易被跳过、也最能拉开差距的环节。

**Hit Rate@k**：前 k 条里是否至少命中一个相关片段。只看有没有，不看排第几。
这是最贴近用户体验的指标——只要答案在前 k 条里，模型就能答出来。

**MRR@k**（平均倒数排名）：命中片段排名的倒数取均值。排第一得 1.0，排第三
得 0.333。它对排序位置敏感，是衡量重排序效果最直接的指标。

**Recall@k**：前 k 条覆盖了多少比例的相关片段。当一个问题对应多个片段时才有
区分度。Hit Rate 会掩盖「只召回一半」的问题，Recall 不会。

三个指标要一起看。只报 Hit Rate 容易自欺：把 k 从 3 调到 20，Hit Rate 一定
好看，但塞进上下文的噪声会拉低生成质量。

## 消融实验

有了评测集就能做消融（ablation）：每次只改动一个环节，量化它带来多少增益。

典型序列是：纯向量基线 → 加入 BM25 双路召回 → 换 RRF 融合 → 加重排序 →
加 HyDE 查询改写。每一组的差值就是这个环节的贡献。

这个做法的价值在于，当面试官问「混合检索到底提升了多少」时，你给的是一个
可复现的数字，而不是「感觉效果好了不少」。前者说明你真做过实验，后者说明
你只是跟着教程跑通了。

同理，HyDE 这类技术不是必然会提升。它对开放域问答有帮助，但面对术语密集的
技术文档经常帮倒忙——因为 LLM 生成的假设答案会引入原文没有的表述，把向量
带偏。跑出负增益并如实报告，比硬说它有效更可信。

## 生成层指标

检索层指标衡量的是「有没有找到」，生成层要衡量「答得对不对」。

**Faithfulness**：回答里的每句论断能否在检索到的上下文中找到依据。低分意味着
模型在编造。这个指标不需要标准答案，只需要上下文，所以标注成本低。

**Answer Relevancy**：回答是否切中问题。识别答非所问的类型。

**Context Recall**：检索到的上下文是否足以支撑标准答案。这是唯一需要人工
标注标准答案的指标，但也是定位问题最准的——它有直接指向「该召回没召回」。

RAGAS 是这几个指标最常用的开源实现，但要注意它内部也调用 LLM 打分，
本身有成本和波动，评测结果应该看趋势而不是绝对值。
