# 向量检索与 Milvus

## 为什么需要向量检索

关键词检索依赖字面匹配。用户问「怎么让回答更准确」，文档里写的是「提升生成质量的方法」，
两者一个词都不重合，倒排索引完全召回不到。向量检索把文本映射到高维空间，
语义相近的文本在空间中距离也近，因此能跨过字面差异找到相关内容。

代价是失去了精确性。向量是语义的模糊压缩，`ERR_CONN_REFUSED` 这种错误码
会被编码成「连接类错误」的大致语义，召回结果里混进一堆连接超时的无关文档。
所以生产系统几乎都同时保留关键词检索，做混合召回。

## 相似度度量

三种常见度量：

- 余弦相似度（COSINE）：只看向量夹角，不看长度。适合文本，因为文本长度
  带来的向量模长差异通常没有语义含义。
- 内积（IP）：夹角和长度都看。当所有向量都做了 L2 归一化之后，内积在数值上
  恒等于余弦相似度，但计算少一步开方，是工程上更常用的选择。
- 欧氏距离（L2）：看绝对距离，对向量模长敏感，文本场景用得少。

关键约束：如果索引用 IP，那么入库向量和查询向量必须都归一化。漏掉这一步
不会报错，只会让检索结果静默变差，是排查成本很高的一类 bug。

## ANN 与 HNSW

精确检索要把查询向量和库里每一条算一遍，十万条 1024 维向量就是十亿次浮点运算，
延迟不可接受。所以实际用的是近似最近邻（ANN），用少量精度换数量级的加速。

HNSW（分层可导航小世界图）是目前主流的图索引。它把向量组织成多层图：
上层稀疏、边长，用于快速跳转；下层稠密、边短，用于精细定位。查询时从顶层
入口点开始贪心下降，逐层收敛到最近邻。

三个关键参数：

- `M`：每个节点在每层的最大出边数，默认 16。M 越大，图的连通性越好，召回率
  越高，但内存占用线性增长，建索引也越慢。1024 维向量的经验值在 16 到 32 之间。
- `efConstruction`：建索引时每插入一个节点要搜索的候选队列长度，默认 200。
  它不直接出现在查询路径上，但决定了图的质量上限。调大能让图更优，代价是
  建索引时间变长。十万级数据 200 通常够用。
- `ef`：查询时的候选队列长度，必须大于等于 top_k。调大提升召回率、增加延迟。
  线上一般取 top_k 的 2 到 4 倍。

三者的关系可以概括为：`efConstruction` 决定图建得好不好，`M` 决定图能连多密，
`ef` 决定查询时愿意搜多深。前者是离线成本，后两者影响线上成本和延迟。

## IVF 索引

IVF（倒排文件索引）先用 k-means 把向量聚成 N 个簇，查询时只在最近的 nprobe
个簇里搜索。参数是 `nlist`（簇数量）和 `nprobe`（查询时搜几个簇）。
相比 HNSW，IVF 内存占用更低，但召回率通常略差，且需要预先训练聚类中心，
数据分布变化后要重建。

数据量在百万以内、延迟要求不极端时，HNSW 是更省心的选择。

## Milvus 架构

Milvus 是存算分离的分布式向量数据库，核心组件：

- etcd：存元数据（collection schema、segment 状态、节点注册信息）
- MinIO 或 S3：存实际数据（向量、日志文件）
- query node：执行向量检索
- index node：后台建索引
- proxy：接收客户端请求，做路由
- root coordinator：管理 DDL 和整体调度

单机部署可以用 embedded etcd 加 local storage 把依赖压到一个容器，
适合开发和演示；生产环境通常拆成独立服务，便于水平扩展。
