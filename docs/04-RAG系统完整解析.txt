一、系统概述
--------------------------------------------------------------------------------

这是一个基于 RAG（Retrieval-Augmented Generation，检索增强生成）架构的
智能知识库问答系统。

核心思想：不让大模型凭空回答，而是先从你的文档里"检索"出相关片段，
再把这些片段"塞"给大模型作为参考资料，让大模型基于真实资料来回答。

技术栈：
  - 后端框架：FastAPI（Python）
  - 前端界面：Streamlit
  - 向量数据库：ChromaDB（本地持久化存储）
  - Embedding 模型：硅基流动 BAAI/bge-m3（把文字转成向量）
  - 大语言模型：DeepSeek（生成回答）
  - PDF 解析：pdfplumber
  - 文档格式支持：.md / .txt / .pdf


二、上传文档完整流程（POST /api/upload）
--------------------------------------------------------------------------------

Step 1：格式校验
  提取文件后缀名（如 .pdf），检查是否在支持的白名单中：
  {".md", ".txt", ".text", ".markdown", ".pdf"}
  不在白名单 → 直接返回 400 错误，拒绝上传。
  注意：白名单里每加一种新格式都需要在后端 app.py 和前端 streamlit_app.py
  两处同时添加。

Step 2：提取文字
  - PDF 文件：用 pdfplumber 库打开并逐页提取文字。
    extract_pdf_text() 是自己写的包装函数，因为 pdfplumber.open()
    需要文件路径，而用户上传时拿到的是内存中的字节流。
    解决办法：先把字节流写入一个临时文件（tempfile），
    再用 pdfplumber 打开临时文件读取文字，读完删除临时文件。
  - TXT/MD 文件：直接用 UTF-8 解码（content.decode("utf-8")）
    因为 TXT 文件本身就是纯文本，不需要额外解析。

Step 3：内容非空检查
  检查提取出来的文字去掉首尾空格后是否为空。
  如果 text.strip() 为空 → 返回 400 错误："文档内容为空"。
  注意：这个检查发生在上传阶段，和后面问答阶段的 collection.count()
  检查是两回事。

Step 4：文本切块（chunk_text 函数）
  参数：
    - CHUNK_SIZE = 500（每块约 500 个字符）
    - CHUNK_OVERLAP = 80（相邻两块之间有 80 个字符重叠）

  为什么要切块？
    大模型的上下文窗口有限，不能一次塞整本书。切成小块后，
    只把最相关的几块发给大模型。

  为什么要有重叠（overlap）？
    防止一句话被刚好切在两块的边界上。
    例如"深度学习是机器学习的分支"这句话如果正好从中间断开：
      块1末尾："深度学习是机"
      块2开头："器学习的分支"
    那么两个块都无法完整表达这句话的意思，检索时两个块都"答不上来"。
    overlap=80 保证了重要语义至少完整出现在一个块里。

Step 5：贴标签（生成 ID 和元数据）
  给每个文本块生成唯一标识：
    - id：{随机8位doc_id}_{块序号}，如 a3f7b2c1_0
    - metadata：{doc_id, source_file, chunk_idx}
  
  标签的作用：后续检索到答案时，能追溯到"来自哪个文件的第几块"。
  这就是前端显示的"来源：简历.pdf - 片段1"。

Step 6：向量化并入库（collection.add）
  调用 ChromaDB 的 collection.add()，传入 ids、documents、metadatas。
  ChromaDB 在存储时会自动调用配置好的 embedding_function（BAAI/bge-m3），
  把每个文本块转成 1024 维的向量，和原文、元数据一起存储。
  
  不需要手动调向量化函数，ChromaDB 内部自动完成。

  持久化目录：~/.rag_chroma_db
  这意味着重启后端后知识库数据不会丢失。

Step 7：返回结果
  返回 JSON：{success, doc_id, filename, chunks, total_chunks}
  chunks 是本次上传切出了多少块，total_chunks 是知识库目前总共多少块。


三、问答完整流程（POST /api/ask）
--------------------------------------------------------------------------------

Step 1：知识库非空检查
  执行 collection.count() 统计知识库中的块总数。
  如果 count == 0 → 返回 400 错误："知识库为空，请先上传文档"。
  
  注意：这里检查的是知识库（向量数据库）里有没有数据，
  而不是检查"上传的文字是否为空"（那个在上传阶段已经检查过了）。

Step 2：语义检索（RAG 的 R —— Retrieval）
  调用 collection.query(query_texts=[用户问题], n_results=min(top_k, count))

  重要澄清：提问不需要切块！
    用户问题通常就一两句话，直接整体转向量即可。
    collection.query() 内部自动完成：
      问题文字 → BAAI/bge-m3 → 1024维向量 → 在向量空间中找最相似的 N 个块

  n_results = min(top_k, count)
    防止 top_k 设得比知识库总数还大。
    例如你设 top_k=4 但库里只有 2 块，就返回 2 块而不是报错。

  top_k 的影响（实际测试过）：
    top_k=2 → 上下文太少，LLM 信息不足，容易产生幻觉（胡编乱造）
    top_k=4 → 刚好，信息充分且精准
    top_k=8 → 噪音过多，混入无关内容，回答啰嗦

  返回的是原文文本片段，不是向量：
    results["documents"][0] → 文字内容
    results["metadatas"][0] → 来源标签（文件名+块编号）
    向量只是中间产物，对用户不可见。

Step 3：拼接上下文
  把检索到的片段格式化为：
    [片段1] 纪赟凯，男，23岁...
    ---
    [片段2] 纪赟凯曾在药明康德实习...

  同时提取来源信息：sources = ["简历.pdf - 片段1", "简历.pdf - 片段2"]

Step 4：组装 System Prompt（Prompt Engineering）
  把上下文和问题填入 Prompt 模板：

  角色约束 + 四条规则：
    1. "严格基于提供的资料，不要编造信息"      → 防幻觉
    2. "如果资料中没有，就说不知道"            → 防胡说八道
    3. "回答末尾标注参考来源"                  → 可追溯
    4. "使用中文回答"                          → 固定语言

  {context} 填入拼接好的检索片段
  {question} 填入用户原始问题

Step 5：发送给 DeepSeek
  两条消息发给 DeepSeek：
    消息1（system）：角色定义 + 资料片段 + 规则约束
    消息2（user）：用户的原始问题

  为什么分两条？
    system 消息告诉 LLM "你是谁"和"有什么参考材料"
    user 消息是"用户具体问了什么"
    这种结构能让 LLM 更好地区分"参考资料"和"待回答的问题"

Step 6：返回结果
  返回 AskResponse {answer, sources}
  - answer：DeepSeek 生成的回答文字
  - sources：来源列表（如 ["简历.pdf-片段1"]），前端会显示给用户


四、常见混淆点澄清（来自学习过程中的踩坑）
--------------------------------------------------------------------------------

1. "text 为空" vs "collection.count() == 0"
   这是两个完全不同阶段的检查：
   - 上传时：检查提取出来的 text.strip() 是否为空（这个 PDF 有没有内容）
   - 问答时：检查 collection.count() 是否为零（知识库里有没有存过数据）
   二者互不相关，不要混淆。

2. "提问需要切块吗？"
   不需要。chunk_text 是用来切长文档的，用户问题通常就一句话，
   直接整体转向量即可。collection.query() 会自动处理。

3. "返回的是向量吗？"
   不是。用户收到的是原文文本片段 + 来源标签。
   向量只是 ChromaDB 内部用来做相似度计算的中间产物。

4. "top_k 是什么？"
   top_k 是一个数字参数（如 4），告诉系统"检索最相似的 K 个片段"。
   返回的不是 top_k 本身，而是 top_k 个文本片段。

5. "embedding 是我手动调的吗？"
   不是。collection.add() 存入时 ChromaDB 自动调用配置好的
   embedding_function（BAAI/bge-m3），不需要手动调。

6. "PDF 解析用的是 pdfplumber 自带函数吗？"
   是的，核心解析用的是 pdfplumber.open() 和 page.extract_text()，
   但 extract_pdf_text() 是自己写的包装函数。
   因为 pdfplumber 需要文件路径，而用户上传的字节流在内存中，
   需要先写入临时文件再解析。

7. "为什么 PyCharm 重启后端后代码没变？"
   旧进程可能没杀干净。lsof -i :8000 查端口占用，
   手动 kill 掉所有旧进程再重启。

8. "为什么 Streamlit 一直重复上传同一个文件？"
   st.rerun() 会导致页面刷新后重新触发上传逻辑。
   解决方案：用 session_state 记录已上传的文件 key，
   上传成功后换 uploader 的 key 来清空组件，避免 rerun。

9. "为什么改了 CHUNK_SIZE 后重新上传才有变化？"
   之前的知识库里的向量是按旧参数切的。
   改了参数后必须重新上传文档，新知识库才会用新参数。


五、技术选型理由
--------------------------------------------------------------------------------

  为什么选 DeepSeek？
    国产大模型，API 价格便宜，中文效果好，兼容 OpenAI 调用格式。

  为什么选 BAAI/bge-m3？
    中文 embedding 效果 Top 级别，免费，通过硅基流动调用。

  为什么选 ChromaDB？
    轻量级向量数据库，不需要额外安装服务端，
    直接 pip install 就能用，有本地持久化，重启不丢数据。

  为什么用 FastAPI？
    异步支持好，自动生成 Swagger API 文档（/docs 页面），
    适合做后端 API 服务。

  为什么用 Streamlit？
    几行代码就能做出交互界面，不需要写 HTML/CSS/JS，
    适合快速验证想法和 Demo 展示。

  为什么用 pdfplumber 而不是 pymupdf（fitz）？
    fitz 在某些环境下对字节流打开不兼容（测试时页数为 0）。
    pdfplumber 更稳定可靠。
