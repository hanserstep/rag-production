# 向量库选型

## 选型的四个维度

向量库没有绝对优劣，只有匹配度。判断时看四件事：数据规模、过滤需求、部署成本、一致性要求。

数据规模在一万条以内，任何方案都够用，甚至用 numpy 做暴力检索都比走网络请求快。
规模到百万级才需要认真考虑索引结构和分片。

过滤需求最容易被低估。真实业务几乎一定有元数据过滤——只搜某个租户的数据、
只搜某个时间范围、只搜某个文档类型。如果一个向量库的过滤是在检索后做（post-filter），
那么过滤条件越严格，召回越少，甚至可能一条都不剩。支持 pre-filter 的库才对。

部署成本包括运维复杂度和依赖数量。Milvus 需要 etcd 和对象存储，Qdrant 单容器就能跑，
pgvector 直接寄生在已有的 PostgreSQL 里。团队没有专职运维时，这个差别很实际。

一致性要求决定能否用最终一致的方案。绝大多数 RAG 场景写少读多，且允许秒级延迟，
所以最终一致足够；但如果是实时更新的知识库（比如工单系统），就要考虑写入可见延迟。

## 常见方案对比

**Milvus** 是功能最全的，支持 HNSW、IVF、DiskANN 多种索引，支持标量过滤和混合检索，
分布式架构能撑亿级。代价是部署组件多（etcd + 对象存储 + 多个 coordinator），
资源占用大，单机跑起来至少 4G 内存。适合有一定规模的正式项目。

**Qdrant** 单二进制部署，Rust 实现，性能和内存效率都不错，过滤能力完整，
支持 payload 索引。中小规模场景下是性价比最高的选择。

**pgvector** 是 PostgreSQL 扩展，优势是能和业务数据放同一个库、同一个事务里，
不用担心向量库和业务库的数据不一致。代价是索引能力较弱，HNSW 参数调节空间小，
数据量超过千万后性能下降明显。适合已有 PostgreSQL 且规模不大的团队。

**FAISS** 是 Facebook 的库而不是数据库，只提供索引和检索，不负责持久化、
元数据、过滤、并发。适合嵌入到自己的服务里做离线检索或评测，不适合直接当服务用。

**Chroma** 定位是开发期工具，API 极简，嵌入式运行，几分钟能跑通。但缺少生产特性：
没有真正的并发控制、不支持分布式、过滤能力弱。适合做原型验证，上线要换。

## 一个容易踩的坑

很多教程把「每个文档建一个 collection」当作示范。这个做法在文档数超过几十之后会崩：

检索时要遍历所有 collection 逐个查询，查询次数随文档数线性增长；
更麻烦的是跨 collection 的分数无法统一比较和排序，因为不同 collection 的
索引参数、数据分布都不同，同一个 query 在不同 collection 上算出的相似度不在一个尺度。

正确做法是单 collection + 文档 id 作为标量字段，检索时用 filter 限定范围。
这样查询永远是 O(1) 次 ANN，且所有结果在同一个尺度下排序。

## 索引参数怎么定

以 HNSW 为例，M 控制图的连通度。M 小则内存省、建索引快，但长距离跳转能力弱，
召回率下降。1024 维向量的常见起点是 16，数据量大会调到 32。

efConstruction 决定建索引时搜索的深度，影响图的质量上限，是离线成本。
它不影响查询延迟，但会显著影响建索引时间。十万级数据 200 通常够用，
百万级建议提到 400 以上。

ef 是查询时的搜索深度，必须大于等于 top_k。它是线上参数，直接权衡召回率和延迟。
经验值是 top_k 的两到四倍，然后压测调优。

三者的关系可以记成：efConstruction 决定图建得好不好，M 决定图能连多密，
ef 决定查询时愿意搜多深。
