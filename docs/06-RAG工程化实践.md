# RAG 工程化实践

## 缓存放在哪一层

RAG 的缓存有四个候选位置，效果和风险各不相同。

**问题级缓存**：把「问题 + 检索参数」哈希成 key，缓存最终答案。命中率取决于
查询重复度。内部知识库场景重复率往往很高（同一个流程图被不同人反复问），
命中率能到 30% 以上。风险是知识库更新后缓存不失效，答案会过期。

**检索结果缓存**：只缓存 embedding 和召回结果，不缓存生成。知识库没变时结果稳定，
变了下一次就更新。粒度比问题级细，更安全。

**Embedding 缓存**：缓存文本到向量的映射。这个几乎无风险——同一个文本的 embedding
永远相同——且收益明确：评测时同一个 query 会被多组配置反复编码，缓存能省掉大部分调用。

**Prompt 前缀缓存**：部分推理服务支持对固定的 system prompt 做 KV cache 复用，
长 system prompt 场景能显著降本。这个不用自己实现，是服务端能力，选型时要问清楚。

工程上的常见组合是：embedding 缓存必做（零风险），检索结果缓存按知识库更新频率设 TTL，
问题级缓存加一个知识库版本号进 key，版本变了自然失效。

## 成本核算

单次问答的成本由三部分组成：embedding、检索、生成。

embedding 成本 = 问题和上下文的总 token 数 × 单价。一次问答通常只编码问题（几十 token），
文档的 embedding 是离线算好存起来的，不重复计费。

检索成本取决于向量库是自建还是托管，自建基本只有机器成本。

生成成本是大头，因为把检索到的上下文塞进 prompt 会显著增加输入 token。
三条上下文各 500 字，约 1500 token，加上问题和 system prompt，一次输入可能 2000 token。
输出通常 200 到 500 token。

控制成本的手段按性价比排序：减少上下文条数（从 5 条降到 3 条）、
压缩上下文（只保留相关句而非整段）、换更便宜的小模型做简单问题、
用缓存避免重复计算。

必须先建立度量再做优化。没有 token 用量和单次成本的数据，所有优化都是猜。

## 可观测性

线上 RAG 出问题时，最常问的三个问题是：这次为什么没检索到、为什么这么慢、为什么这么贵。

回答这三个问题需要在一次请求内记录：query 原文、改写的 query（HyDE 后）、
各路召回的候选数和耗时、融合后的排序、重排分数、最终进入 prompt 的上下文、
LLM 的 token 用量和耗时。

这些信息必须挂在同一个 trace_id 下，输出成一行 JSON。分散在多行的日志在出问题时
需要人工拼接，而一次请求可能产生十几行，拼错的概率很高。

除了单请求排查，还需要聚合指标：P50/P95/P99 延迟、缓存命中率、
召回条数的分布（如果长期是 0，说明知识库覆盖不足）、拒答率
（如果长期为 0，说明阈值设得太松，模型在硬答）。

## 拒答与阈值

检索增强系统最容易被忽略的是「不知道怎么答的时候怎么办」。

如果无条件取 top 3 交给模型，那么知识库没有相关内容时，模型会基于三条不相关的
片段编出答案，而且语气自信。这是 RAG 幻觉最主要的来源。

正确做法是给相关性分数设阈值，低于阈值的直接丢弃；一条不剩就明确告知
「知识库中没有相关内容」。这个改动在 Prompt 层面基本无法替代——
在 system prompt 里写「不要编造」的收敛效果很差，因为模型看到上下文里有内容，
就会倾向于使用它。

阈值怎么定：拿一批「应该拒答」的问题（比如问知识库完全没覆盖的领域），
看它们的重排分数分布，取一个能过滤掉大部分的分位点。宁可多拒答，
也不要给出自信的错误答案——前者用户会换个问法，后者用户会失去信任。

## 增量更新

知识库不是静态的。文档新增、修改、删除都要反映到索引里。

关键设计是**按文档 id 做原子替换**：删除该文档的所有旧 chunk，再写入新 chunk。
而不是在旧数据上追加，否则会留下孤儿片段，检索时召回到已经删除的内容。

BM25 索引也要同步更新，否则会出现「向量库删了但关键词还能搜到」的诡异现象。
这就是为什么两路索引必须以同一个 doc_id 为单位管理生命周期。

如果索引很大、无法整库重建，就要维护 chunk 级别的幂等 id（文档 id 加 chunk 序号），
写入时 upsert 而非 insert。这也是本项目把 chunk id 设计成「doc_id#序号」的原因。
